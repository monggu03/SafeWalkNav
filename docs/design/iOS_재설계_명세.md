# SafeWalk iOS 재설계 명세

> 작성: 2026-07-13 (서울임팩트 단계)
> 상태: **설계 확정. 개발 착수 전.**
> 이 문서는 iOS UI 전면 재설계의 기준 명세입니다. 코드는 이 문서를 따릅니다.

---

## 0. 왜 다시 만드는가

기존 iOS UI(탭 2개 구조)를 폐기하고 처음부터 다시 만듭니다. 이유는 셋입니다.

1. **실제 시각장애인 테스트에서 조준에 실패했습니다.** 사용자들이 폰을 앞으로 제대로 드는 것도, 방향을 찾는 것도 힘들어했습니다.
2. **탭 구조가 VoiceOver 사용자에게 부적합합니다.** 특히 횡단보도 접근 시 자동으로 탭이 바뀌면, 화면을 볼 수 없는 사용자는 방향을 완전히 잃습니다.
3. **벤치마크(OKO)가 훨씬 단순한 방식으로 이 문제를 이미 풀었습니다.**

## 1. 설계 원칙

| 원칙 | 뜻 |
|---|---|
| **오안내하기보다 침묵한다** | 확신이 없으면 아무 말도 하지 않습니다. 침묵도 정보입니다. |
| **최종 판단은 사용자에게** | 앱은 *"건너세요"* 라고 말하지 않습니다. 신호 색만 알립니다. |
| **단순함이 곧 안전이다** | 횡단보도 앞은 시끄럽고 긴장됩니다. 상태가 많으면 그 혼란 자체가 사고 원인입니다. |
| **평소엔 침묵, 횡단보도에서만 깨어난다** | 시각장애인은 흰지팡이로 이미 잘 걷습니다. 앱이 계속 떠들면 방해입니다. |
| **보행 기술을 대체하지 않고 보완한다** | OKO와 동일한 태도. 앱은 도구이지 눈이 아닙니다. |

## 2. 범위

### 만드는 것
- 음성으로 목적지 입력 → TMap 경로 탐색
- 경로상 **횡단보도 위치** 파악 → 25m 이내 진입 시 자동 활성화
- **신호등 인식** (CoreML) → 빨강/초록 판정
- **진동 + 소리 + 화면 색**으로 신호 상태 전달
- 횡단보도가 **몸 기준 어느 방향**인지 안내 (GPS)
- 잔여시간 음성 안내 (T-Data, 네트워크 있을 때만)

### 만들지 않는 것 (의도적 제거)
- ❌ **"3시 방향에 카메라를 들어주세요"** 카메라 조준 안내 — 실사용자가 이걸로도 못 했고, OKO는 이것 없이 성공했습니다
- ❌ 걷는 중 좌우 방향 보정 (*"약간 오른쪽으로 가세요"*)
- ❌ 곡선·회전 사전 안내 (*"곧 왼쪽으로 휘어집니다"*)
- ❌ 거리 안내 (*"80미터 더 이동하세요"*)
- ❌ BLE 음향신호기 (규격 확보 후 재검토)
- ❌ 탭 구조 — **화면은 하나입니다**

## 3. 조준 — OKO 방식 채택

### 사용자에게 요구하는 것은 이것 하나뿐입니다

> **"휴대폰을 가슴에 대고, 카메라가 앞을 향하게 하세요."**

**몸이 조준 장치입니다.** 폰이 아닙니다.

- 가슴에 대면 폰이 **자연스럽게 수직으로 섭니다** → 상하(기울기) 문제 해결
- 몸이 향한 방향 = 건너려는 방향 → 좌우(방향) 문제 해결
- 시각장애인은 **자기 몸이 어디를 향하는지는 압니다.** 폰이 어디를 향하는지는 모릅니다.

### 조준 안내는 하지 않습니다. 감지 피드백이 곧 조준 안내입니다

신호등이 카메라에 잡히는 **순간 즉시 진동·소리가 시작됩니다.** 사용자는 그 피드백을 듣고 자세를 유지합니다.

- 신호등이 안 잡히면 → **완전한 무음·무진동**
- 10초가 지나도 못 찾으면 → 딱 한 번만: *"신호등이 보이지 않습니다. 몸을 조금 돌려보세요."*

**억지로 "왼쪽으로, 위로" 안내하지 않습니다.** 침묵이 "지금 못 보고 있다"는 신호입니다.

> ⚠️ **즉각성이 이 설계의 생명입니다.** 신호등이 화면에 들어왔는데 피드백이 1초 늦으면, 사용자는 이미 자세를 바꿔버립니다. (§8 프레임레이트 참조)

## 4. 신호 상태 — 빨강 / 초록 두 개뿐

| 상태 | 판정 |
|---|---|
| **빨강** | 적색 신호 **또는 초록 점멸** |
| **초록** | 정상 초록 신호 |
| **(무음)** | 신호등이 인식되지 않음 |

### 점멸은 빨강입니다

판정 기준은 **"지금 출발해도 되는가"** 입니다.

초록 점멸의 의미는 *"이미 건너는 중이면 서둘러 마저 건너라, **새로 출발하지는 마라**"* 입니다. 이때 초록 신호를 주면 **막 도착한 사람이 출발합니다.** 가장 위험한 시나리오입니다.

따라서 **점멸 = 빨강**입니다. (이미 건너는 중인 사람은 어차피 계속 갑니다.)

### 왜 상태를 늘리지 않는가

*"안전한 초록"* 과 *"확인 불가 초록"* 을 구분하는 안을 검토했으나 **폐기했습니다.**

- **전환을 감지하는 것은 앱이 아니라 사용자입니다.** 사용자는 빨강 진동을 계속 느끼다가 그것이 초록 진동으로 **바뀌는 것을 몸으로 겪습니다.** 그 변화 자체가 "방금 바뀌었다"는 정보입니다.
- 횡단보도 앞에서 상태가 5개인 앱은 위험합니다. 긴장한 상태에서 헷갈리면 그 혼란이 사고 원인이 됩니다.

### 남는 위험 — 정직하게 기록

도착했더니 **이미 초록이고 실제로는 2초 남은 경우**, 앱은 이를 구분할 수 없습니다.

다만 **이는 눈 뜬 사람도 동일하게 겪는 위험입니다.** 초록불을 보고 건너다 중간에 빨강이 되는 일은 누구에게나 일어납니다. 앱이 시각장애인을 정안인보다 못한 상태로 만들지는 않습니다.

이 위험은 **잔여시간 음성(§5)** 으로 부분 완화합니다.

## 5. 피드백 채널 — 감각별로 분리

**채널을 나누면 상태를 늘리지 않고도 정보를 더할 수 있습니다.**

| 채널 | 전달 내용 | 비고 |
|---|---|---|
| **진동 + 소리 (리듬)** | **빨강 / 초록** | 2가지뿐. 절대 늘리지 않습니다 |
| **화면 전체 색** | **빨강 / 초록** | 저시력자·동행자·시연용 |
| **음성** | 잔여시간, 25m 진입 알림, 조준 안내(1회) | T-Data 없으면 잔여시간은 말하지 않습니다 |
| **무음·무진동** | 신호등 인식 안 됨 | 침묵도 정보입니다 |

### 진동이 소리보다 우선입니다

**횡단보도는 차 소리로 시끄럽습니다.** *"초록불입니다"* 라는 음성은 묻힙니다. **진동은 안 묻힙니다.**

특히 **빨강 → 초록 전환 순간**에는 **강한 진동이 소리보다 먼저** 나가야 합니다.

### 화면 색은 장식이 아닙니다

**시각장애인 중 상당수는 완전 실명이 아닙니다.** 작은 아이콘은 못 봐도, **화면 전체가 빨강인지 초록인지는 인지하는 저시력자가 많습니다.** 이들에게 화면 색은 실제 정보입니다.

동행자·보호자, SOVAC 부스 시연에도 그대로 사용됩니다.

### 잔여시간은 음성이라는 별도 채널로

진동/리듬은 **빨강·초록 2개로 고정**하고, 잔여시간은 음성으로 얹습니다.

> *"3초 남았습니다"*

**진동으로 색을 알고, 귀로 시간을 압니다.** 서로 다른 감각이라 섞이지 않습니다. 상태를 늘리지 않고 정보만 추가됩니다.

**이것은 OKO가 하지 못하는 부분입니다.** OKO에는 잔여시간 데이터가 없습니다.

## 6. 횡단보도 30초 — 전체 시나리오

### ① 이동 중 — 침묵
GPS만 봅니다. 카메라 꺼짐. 아무 말도 하지 않습니다. 사용자는 평소처럼 흰지팡이로 걷습니다.

### ② 25m 진입 — 깨어남
짧은 알림음 + 진동. 그리고 한 마디.
> *"횡단보도입니다. 3시 방향입니다."*

**카메라 조준이 아니라 몸을 돌리라는 뜻입니다.** GPS가 할 수 있는 유일하고 확실한 일입니다.

### ③ 조준 — 말은 딱 한 번
> *"휴대폰을 가슴에 대고 앞을 향해 주세요."*

이후 **말하지 않습니다.** 카메라가 켜지고, 신호등이 잡히는 순간 리듬이 시작됩니다.

### ④ 신호 상태 — 리듬으로 전달
- **빨강**: 느린 리듬 + 약한 진동 + 화면 빨강
- **초록**: 빠른 리듬 + 강한 진동 + 화면 초록
- **안 보임**: 무음, 무진동

### ⑤ 빨강 → 초록 전환 — 이 순간이 전부
- **강한 진동 즉시** (소리보다 먼저)
- 리듬이 빠르게 전환
- 화면 초록

**"건너세요"라고 말하지 않습니다.** 판단은 사용자가 합니다.

### ⑥ 건너는 중
빠른 리듬 유지. 점멸이 감지되면 **빨강으로 전환**됩니다(= 출발 금지 신호). 이미 건너는 중인 사용자는 계속 진행합니다.

### ⑦ 통과 — 다시 침묵
GPS로 zone 이탈 감지 → 짧은 완료음 → 카메라 끄고 조용해집니다.

## 7. VoiceOver 정책

**전제: 사용자는 VoiceOver를 켜고 씁니다.** (한국 시각장애인 다수)

| 누가 말하나 | 무엇을 |
|---|---|
| **VoiceOver** | 버튼·목록·상태 등 **화면 요소** (`accessibilityLabel` / `Hint` / `Traits`) |
| **앱 TTS** | VoiceOver가 알 수 없는 **실시간 세계** (신호등, 조준, 경고, 잔여시간) |

### 충돌 처리

| 급함 | 처리 |
|---|---|
| **R→G 전환, 위험 경고** | 앱이 **즉시** 발화 + VoiceOver ducking. **진동이 우선** |
| 잔여시간, 조준 안내 | 앱이 직접 짧게 발화 |
| 경로 요약, 목적지 확인, 화면 안내 | VoiceOver에 위임 (`UIAccessibility.post(.announcement)`) |

**우리가 새로 만들 음성은 "VoiceOver가 절대 못 하는 것"뿐입니다.** VoiceOver는 사용자가 매일 쓰는 도구이고, 우리가 그걸 대체하려 들면 오히려 낯설어집니다.

## 8. 기술 파라미터

### 프레임레이트 — 단계별로 다르게

**조준 중 즉각성이 이 설계의 생명입니다.** 지금처럼 초당 3회(333ms 스킵)로는 조준 피드백이 최대 1초 늦습니다.

| 단계 | 프레임레이트 | 이유 |
|---|---|---|
| **조준 중** (신호등 탐색) | **초당 10~15회** | 즉각 피드백이 조준의 전부 |
| 상태 유지 중 (이미 찾음) | 초당 3회 | 배터리 절약. 상태는 천천히 변함 |
| **R→G 감시 중** | **초당 10~15회** | 전환 순간을 놓치면 안 됨 |

아이폰 NPU 추론이 3~8ms이므로 **초당 10회는 부담이 아닙니다.** 조준하는 몇 초 동안만 빠르게 돌리면 배터리 영향은 미미합니다.

### 오프라인 정책 — 안전의 최저선

> **신호등 인식만큼은 네트워크 없이도 100% 동작해야 합니다.**

| 기능 | 네트워크 | 없을 때 |
|---|---|---|
| **신호등 인식 (CoreML)** | 불필요 | **정상 동작** ✅ |
| **신호등 위치 DB** | 최초 1회 | **캐시 사용** ✅ |
| 잔여시간 (T-Data) | 필요 | **그냥 말하지 않음** |
| 목적지 검색 (TMap) | 필요 | **"신호등만" 모드로 동작** |

**네트워크가 죽어도 앱을 켜면 신호등은 읽어줍니다.** 횡단보도 앞에서 앱이 먹통이 되는 건 위험합니다.

*(참고: OKO는 완전 오프라인 동작입니다. 이 점은 우리가 뒤처져 있었습니다.)*

## 9. 화면 구조

**화면은 하나입니다. 탭은 없습니다.**

상황에 따라 그 하나가 변합니다. 사용자는 "지금 앱이 뭘 하고 있는지"만 알면 됩니다.

```
① 대기       "목적지를 말해주세요"
② 듣는 중     (음성 인식)
③ 결과 선택   POI 1~5개, 큰 버튼, VoiceOver 더블탭으로 선택
④ 이동 중     ← 조용합니다
⑤ 횡단보도    ← 화면 전체가 빨강/초록. 앱의 존재 이유
⑥ 도착
```

### 첫 실행 시 사용법 학습 (필수)

OKO도 첫 실행 시 training을 제공합니다. 우리도 필요합니다. 특히 가르쳐야 할 것:

- **"가슴에 대고 앞으로"** 자세
- **빨강 진동 / 초록 진동**을 실제로 들려주고 느끼게 함
- **무음 = 신호등을 못 보고 있다**는 뜻
- **앱이 "건너세요"라고 말하지 않는다**는 것 — 판단은 본인이 합니다

## 10. OKO 대비 차별점

**OKO는 한국 보행자 신호등을 인식하지 못합니다** (동국대 인근 실측 확인).

이유는 명확합니다. 한국 보행자 신호등은 **사람 형상(적/녹) 픽토그램**인데, OKO는 유럽·미국 신호등으로 학습했습니다. **학습 데이터에 없는 물체는 보지 못합니다.**

| 항목 | OKO | SafeWalk |
|---|---|---|
| **한국 신호등 인식** | ❌ **불가** | ✅ 한국 데이터 학습 |
| 잔여시간 | ❌ 없음 | ✅ 서울 T-Data |
| 횡단보도 위치 안내 | ❌ 없음 | ✅ GPS 기반 |
| 조준 방식 | 가슴+앞, 즉각 피드백 | **동일 (채택)** |
| 오프라인 | ✅ 완전 | 🟡 인식은 가능 |

> ⚠️ **이 우위는 영구적이지 않습니다.** OKO가 한국 데이터를 학습하면 사라집니다. 장기 해자는 AI 모델이 아니라 **한국 인프라와의 결합**(T-Data, BLE 음향신호기, 지자체 관계)입니다.

### 반드시 만들어야 할 증거

**같은 횡단보도에서 두 앱을 나란히 켠 영상.** OKO는 침묵하고, SafeWalk는 인식하는 대비 영상. 이것이 실로암 제안·관악구청 정책 제안·SOVAC 부스에서 가장 강력한 자산이 됩니다.

## 11. 미결정 — 7월 사용자 테스트로 확정할 것

**책상에서 정하지 않습니다.** 다음은 실제 사용자에게 물어봐야 합니다.

| 항목 | 확인 방법 |
|---|---|
| 리듬 파라미터 (간격, 주파수) | "이 소리가 무슨 뜻 같으세요?" |
| 진동 패턴 (빨강/초록 구분) | 실제로 느끼게 하고 구분 가능한지 |
| 이미 초록일 때 어떻게 하길 원하는지 | "한 주기 기다리는 게 나은가, 그냥 알려주는 게 나은가" |
| 참여자들이 **VoiceOver를 쓰는지** | 실로암 컨택 시 확인 |
| **골전도 이어폰 유무** | 없어도 동작해야 하므로 진동이 중요 |
| 참여자들이 **안드로이드/아이폰 중 뭘 쓰는지** | iOS 재개발의 전제가 되는 사실 |

### 별도 실측 필요

| 항목 | 방법 |
|---|---|
| **초광각 렌즈 사용 여부** | 초광각으로 찍은 한국 신호등에 현재 모델을 돌려본다. 시야각이 넓으면 조준이 쉬워지지만(73°→120°), 신호등이 작아져 인식률이 떨어질 수 있다 (30m 기준 31px → 19px). **실측 없이 결정하지 않는다.** |
| iOS 실기기 추론 속도 | Mac 확보 후 측정. 초당 10~15회가 가능한지 확인 |
