# SafeWalk 기술 총정리

> 기준: 2026-07-14, `origin/main` (PR #76) + 검출 필터 재설계 반영
> **이 문서는 "실제 코드에 존재하는 것"만 적습니다.** 기획했지만 안 만든 것, 만들었다가 지운 것은 §7에 따로 적습니다.

## 1. 한 줄 정의

**시각장애인이 횡단보도를 건널 때, 신호등 색을 카메라로 읽어 진동·소리로 알려주는 앱.**

핵심 원칙은 하나입니다.

> **오안내하기보다 침묵한다.**
> 앱은 *"건너세요"* 라고 말하지 않습니다. 신호 상태만 알리고, 판단은 사용자가 합니다.

---

## 2. 구조 — KMM (Kotlin Multiplatform Mobile)

비즈니스 로직을 한 번만 쓰고 안드로이드·iOS가 공유합니다.

```
shared/       ← 공통 로직 (Kotlin). 네비게이션, 신호등 매칭, 좌표 수학, 안내 문장
androidApp/   ← 안드로이드 UI + 센서 + 카메라 + TFLite 추론
iosApp/       ← iOS UI + 센서 + 카메라 + CoreML 추론
```

플랫폼 의존적인 부분(시간, 로그, GPS 타입)만 `expect/actual` 로 분리했습니다.

**의미:** 신호등 판정 로직·안전장치를 두 번 구현하지 않습니다. 안전 규칙이 두 OS에서 어긋날 위험이 구조적으로 없습니다.

## 3. AI 모델 — 신호등 인식

> **⭐ 2026-07 방침 변경: 자체 모델(P2 Head)을 접고, 검증된 오픈소스 모델을 쓴다.**
> 이유는 아래 §3.3 에 적습니다. 이건 후퇴가 아니라 **문제의 진짜 원인을 찾은 결과**입니다.

### 3.1 현재 채택 모델 — kairess (오픈소스)

| 항목 | 값 |
|---|---|
| 출처 | [`kairess/crosswalk-traffic-light-detection-yolov5`](https://github.com/kairess/crosswalk-traffic-light-detection-yolov5) |
| 목적 | "시각장애인을 위한 횡단보도·신호등 검출" — **우리와 같은 목적** |
| 아키텍처 | YOLOv5s6 (P6), 12.3M params, 입력 640×640 |
| 학습 데이터 | **SelectStar 위씨(WeSee) 한국 교차로 6,593장 / 9,120 라벨** |
| 클래스 | `Zebra_Cross`(0), `R_Signal`(1), `G_Signal`(2) |
| 성능 | mAP@.5 **0.956** / 빨강 0.941(recall 0.934) / 초록 0.940(recall 0.926) |
| 라이선스 | GPL-3.0 |

**채택 이유는 하나입니다: 데이터가 8배입니다.** 우리 939장 vs 6,593장.
소량 데이터로 아키텍처를 쥐어짜는 것보다, **같은 목적으로 8배 데이터에 학습된 검증된 모델을 쓰는 게 빠르고 안전합니다.**

앱은 클래스를 리매핑해서 받습니다: `R_Signal → 빨강(0)`, `G_Signal → 초록(1)`, `Zebra_Cross`는 무시.
**앱 계약은 불변입니다 — 모델이 무엇이든 `classId 0=빨강, 1=초록`.**

### 3.2 자체 모델 (P2 Head) — 폴백 겸 프로젝트 자산

`TrafficLightDetector.ACTIVE_MODEL` 상수 **한 줄**로 두 모델을 전환합니다. 자체 모델은 폴백으로 남깁니다.

| 항목 | 값 |
|---|---|
| 아키텍처 | YOLOv11n + **P2 Head** (자체 yaml 설계) |
| 데이터 / 성능 | 939장 / mAP50 0.947 |
| 크기 | Float16 5.6 MB |

Ultralytics 가 YOLOv11용 P2 yaml 을 제공하지 않아, YOLOv8-P2 패턴을 가져와 레이어 인덱스를 재매핑하고 C2f → C3k2 로 치환해 직접 설계했습니다. P2는 stride 4 를 추가해 격자를 80×80 → **160×160** 으로 촘촘하게 만듭니다(작은 물체용).

**이 작업 자체는 유효한 공학적 기여이고 캡스톤 산출물로 남습니다.** 다만 §3.3 의 이유로 **주력에서 내렸습니다.**

### 3.3 ⭐ 왜 방침을 바꿨나 — 진짜 원인은 모델이 아니었다

**"모델이 원거리 신호등을 인식 못 한다"** 가 P2 Head 를 만든 이유였습니다.
그런데 실기기 로그를 파보니 **모델은 잡고 있었고, 앱이 버리고 있었습니다.**

앱의 bbox 크기 필터가 빨강 3% / 초록 6% 였습니다. 신호등 픽토그램 30cm, 화각 70° 기준 화면 비율은 대략 `0.214 / 거리(m)` 입니다.

| 거리 | 화면 비율 | 구 필터 |
|---|---|---|
| 4m | 5.4% | 빨강 O / 초록 O |
| 7m | 3.1% | 빨강 O / **초록 X** |
| 20m | 1.1% | **둘 다 X** |
| 30m | 0.7% | **둘 다 X** |

→ **빨간불은 7m, 초록불은 4m 안에서만 통과했습니다.**
정작 필요한 건너편 신호등(20~50m)은 **모델이 정확히 잡아도 앱이 전부 버렸습니다.** (로그: `ALL_TOO_SMALL`)

**아키텍처로 풀려던 문제가 사실은 상수 두 개짜리 버그였습니다.**
필터를 고친 지금, 원거리 성능을 아키텍처로 쥐어짤 이유가 사라졌습니다.
**우리의 기여는 모델이 아니라 §4 안전 설계와 §6 인프라 결합에 집중합니다.**

> ⚠️ **여전한 한계:** kairess 모델도 **한국 데이터만** 학습했습니다.
> 미국 보행 신호는 **흰색 걷는 사람 / 주황색 손바닥**(MUTCD) 이라 **현재 어떤 모델로도 인식하지 못합니다.**

## 4. 안전 설계 — 층층이 거른다

AI 하나만 믿지 않습니다. 오탐이 사람을 차도로 내보내기 때문입니다.
**비대칭이 핵심입니다: 초록 오탐(사고)이 빨강 오탐(괜히 기다림)보다 비교할 수 없이 위험합니다.**

| 층 | 내용 | 값 |
|---|---|---|
| **1. Zone 게이팅** | TMap 경로상 횡단보도 25m 이내에서만 카메라·안내 작동 | `CrosswalkGuard`, 25m |
| **2. 크기 하한** | 서브픽셀 노이즈 제거. 두 색 공통 | bbox ≥ **0.8%** (≈27m) |
| **3. 신뢰도 (비대칭)** | **여기에 안전 마진을 건다** | 빨강 **0.25** / 초록 **0.45** |
| **4. 시간적 안정성** | 연속 프레임 확정 | 빨강 **2**프레임 / 초록 **3**프레임 |
| **5. 점멸(Flicker) 감지** | 초록 점멸 = 출발 금지 → 안내 차단 | 감지 시 락아웃 |
| **6. 발화 원칙** | *"건너세요"* 를 말하지 않음. 색만 알림 | — |

### 최근에 고친 중대한 결함 (2026-07-13)

기존에는 **크기**로 안전 마진을 걸었습니다 (빨강 3% / 초록 6%).
신호등 픽토그램 30cm, 화각 70° 기준 화면 비율은 대략 `0.214 / 거리(m)` 입니다.

| 거리 | 화면 비율 | 구 필터 |
|---|---|---|
| 4m | 5.4% | 빨강 O / 초록 O |
| 7m | 3.1% | 빨강 O / **초록 X** |
| 20m | 1.1% | **둘 다 X** |
| 30m | 0.7% | **둘 다 X** |

→ **빨간불은 7m, 초록불은 4m 안에서만 통과했습니다.**
정작 필요한 **건너편 신호등(20~50m)은 모델이 정확히 잡아도 앱이 전부 버렸습니다.**
"모델이 인식을 못 한다"의 진짜 원인은 모델이 아니라 이 필터였습니다.

**수정:** 크기는 물리적 하한선(0.8%)으로만 쓰고, **안전 마진은 신뢰도와 시간적 안정성으로 옮겼습니다.**
멀리 있는 *진짜* 초록불은 살아남고, 가까이 있는 *가짜* 초록불(후미등·간판)은 신뢰도에서 걸립니다.

## 5. 내비게이션 — 횡단보도까지 데려다주기

### 경로
- **TMap 보행자 경로 REST API** (Ktor). 지도 SDK 는 쓰지 않습니다 — 화면을 볼 수 없는 사용자에게 지도는 의미가 없습니다.
- 음성으로 목적지 입력(STT) → POI 검색 → 경로 수신

### 경로 사전 분석 — `RouteAnnotator`
경로 전체를 미리 훑어 각 구간을 분류합니다:
`STRAIGHT / SLIGHT_CURVE / CURVE / SLIGHT_TURN / TURN / SHARP_TURN`

그리고 **도달하기 전에 미리** 말합니다.
- 예고(15~30m 전): *"곧 왼쪽으로 크게 꺾습니다."*
- 직전(~5m): *"지금 왼쪽으로"*

TMap 폴리라인은 곡선 정보가 성기므로, 누적 곡률을 분석해 **5m 간격 가상 waypoint** 를 삽입합니다.
(보행 속도 1.44 m/s — Clark-Carter 1987, 시각장애인 보행 속도 연구 근거)

### 방위(heading) — `KalmanHeading`
**Circular Kalman Filter.** 방위각은 원형(0°=360°)이라 일반 칼만 필터를 쓰면 350°와 10° 사이에서 터집니다.
→ **sin/cos 두 직교 성분으로 분해**해 각각에 1D 칼만을 적용한 뒤 다시 합칩니다.
GPS accuracy 를 measurement noise 로 동적 사용합니다.

## 6. 한국 인프라 결합 — 이게 진짜 해자

**AI 모델은 언젠가 따라잡힙니다. 인프라 결합은 안 그렇습니다.**

| 데이터 | 용도 |
|---|---|
| **서울시 신호등 위치 공공데이터** (약 62,690건) | 횡단보도가 몸 기준 몇 시 방향인지 (*"3시 방향입니다"*) |
| **서울시 T-Data 신호 잔여시간 API** | *"3초 남았습니다"* — **OKO에는 없는 기능** |
| **Room 캐시** | 신호등 위치를 로컬 DB에 저장 → 오프라인에서도 방향 안내 가능 |

### `TrafficSignalMatcher` — 4단계 매칭
카메라에 잡힌 신호등이 **어느 횡단보도의 것인지** 특정합니다.
1. GPS 반경 50m 후보 추출
2. 전방 90° 우선
3. TMap 경로상 횡단보도와의 거리 가중
4. 반대편(= 내가 볼) 신호등 우선

잔여시간 API 는 60초 쿨다운으로 호출량을 제어합니다.

## 7. 온보딩 · 피드백

- **`AutoOnboardingCoordinator`** — 5단계 상태기계 (요약 → 자세 → 회전 → 확인 → 완료)
  - `PoseSensor` (중력): 폰을 평평하게 들었는지
  - `HeadingSensor` (나침반): 출발 방향을 향했는지
  - **실시간 스테레오 비프**로 방향 유도 — 목표에 가까울수록 삐 소리가 빨라짐 (말로 "왼쪽 30도" 하는 것보다 훨씬 빠름)
- **`SpatialBeeper`** — 좌우 패닝 오디오. 방향을 소리의 위치로 전달
- **TTS/STT** — 음성 입출력
- **`SafetyNoticeActivity`** — 첫 실행 시 안전 고지 동의 게이트

## 9. 폐기한 것 — 정직하게

**만들었다가 정량 검증 후 버린 기술입니다. 이걸 말할 수 있는 게 오히려 강점입니다.**

| 기술 | 왜 버렸나 |
|---|---|
| **Depth Anything V2** (단안 깊이 추정) | 줄자 실측 결과 5m 이내만 신뢰 가능, 7m↑ 에서 51% 오차 + 거리 역전. 차량 회피에 필요한 40~60m 와 괴리. 인터뷰에서도 "위험 탐지보다 내비·신호등이 중요"가 일관됨 |
| **IMU 기반 heading** | 정지 시엔 안정적이나 보행 중 재현성 부족 (동일 조건 4회 보행에 급변율 3.9~18.1% 편차). GPS Kalman 단일 소스로 일원화 |
| **보행 중 좌우 보정** (*"약간 오른쪽으로"*) | 실사용자에게 혼란만 줌. 흰지팡이 사용자는 이미 직진을 잘함 |
| **TrustBasedNavigator / ForwardOnlyTracker** | 복잡도 대비 이득 없음 |
| **OpenCV** | 유일 사용처가 임시 검증 파일이었음. 제거로 **APK 186MB → 31.6MB** |
| **BLE 음향신호기** | 경찰청 규격 미확보. 시간 남으면 재검토 |
| **자체 P2 Head 모델 (주력에서)** | 만든 이유였던 "원거리 인식 실패"의 진짜 원인이 **앱의 크기 필터 버그**로 밝혀짐. 8배 데이터로 학습된 오픈소스(kairess)로 교체. 코드에는 폴백으로 남김 |

## 11. OKO 대비

**OKO는 한국 보행 신호등을 인식하지 못합니다** (동국대 인근 실측 확인). 유럽·미국 데이터로 학습해서, 한국의 사람 형상 픽토그램을 못 봅니다.

| | OKO | SafeWalk |
|---|---|---|
| 한국 신호등 | ❌ | ✅ |
| **미국 신호등** | ✅ | ❌ **(우리 약점)** |
| 잔여시간 | ❌ | ✅ (T-Data) |
| 횡단보도 방향 안내 | ❌ | ✅ (GPS + 공공데이터) |
| 오프라인 | ✅ 완전 | 🟡 인식은 가능 |
| 조준 방식 | 가슴+앞, 즉각 피드백 | 동일 방식 채택 |

> **이 우위는 영구적이지 않습니다.** OKO가 한국 데이터를 학습하면 사라집니다.
> **장기 해자는 AI가 아니라 한국 인프라 결합**(T-Data, 음향신호기, 지자체 관계)입니다.
